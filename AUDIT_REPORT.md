# Аудит проекта Status Stock
Дата: 1 декабря 2025

## Критические проблемы (блокеры релиза)

- [ ] [bot/utils/api.js:135] **Сломана аутентификация бота**
  Функция `createProduct` (и другие методы изменения данных) делает POST-запрос на `/api/products`, но не передает заголовок `Authorization`. В `backend/src/routes/products.js` (строка 14) маршрут защищен middleware `verifyToken`. Бот получит ошибку `401 Unauthorized` при попытке создать товар.
  *Риск:* Бот полностью нефункционален для продавцов (нельзя добавить товар).

- [ ] [backend/src/services/productSyncService.js:77-110] **Отсутствие транзакции при копировании товара**
  В функции `copyProductWithMarkup` создание товара (`productQueries.create`) и создание записи о синхронизации (`syncedProductQueries.create`) происходят как две независимые операции вне транзакции. Если вторая операция упадет (сбой сети/БД), в магазине подписчика останется "сирота" — копия товара, которая никак не связана с оригиналом и не будет обновляться.
  *Риск:* Замусоривание БД дубликатами товаров, рассинхронизация цен.

## Серьёзные проблемы (нужно исправить)

- [ ] [bot/bot.js:28] **Хранение сессий в оперативной памяти**
  Используется дефолтная конфигурация `session()`, которая хранит состояние (формы добавления товара, корзину) в RAM. При любом перезапуске бота (деплой, падение) все пользователи потеряют свои незавершенные действия.
  *Риск:* Плохой UX, потеря данных пользователей.

- [ ] [backend/src/controllers/shopFollowController.js:420-424] **Partial Failure при создании подписки**
  Транзакция коммитится (line 420) *до* постановки задачи синхронизации в очередь (line 424). Если `queueProductSync` упадет (например, Redis недоступен), подписка будет создана, но товары не скопируются. Статус останется `active`, но магазин будет пуст.
  *Риск:* Подписчик видит пустой магазин и думает, что сервис не работает.

- [ ] [backend/src/services/productSyncService.js:335-338] **Race Condition при обновлении наценки**
  В функции `updateMarkupForFollow` используется транзакция и блокировки, но проверка существования `followResult` (line 338) и последующий `ROLLBACK` могут вызвать ошибку "Transaction not found" в логах, если транзакция уже была автоматически сброшена драйвером (хотя здесь используется явный клиент, так что риск меньше, но логика обработки ошибок требует внимания).

## Мелкие проблемы (желательно исправить)

- [ ] [backend/src/middleware/telegramAuth.js:67] **Логирование чувствительных данных**
  В режиме DEBUG логируются части хешей (`calculatedHash`, `providedHash`). Хотя они обрезаны, в security-логах лучше избегать вывода любых криптографических материалов.

- [ ] [backend/src/routes/follows.js:16] **Дублирование параметров запроса**
  Логика `if (req.query.shop_id && !req.query.shopId)` выглядит как "костыль" для поддержки разных стилей именования (snake_case vs camelCase). Лучше привести API к единому стандарту на уровне валидации.

## Потенциальные улучшения (не баги, но стоит сделать)

- [ ] **Централизация API клиента для бота**
  Сейчас `bot/utils/api.js` не имеет механизма авторизации (получения токена). Стоит реализовать механизм "System Token" или "Bot Token", который бекенд будет принимать для сервисных операций, либо реализовать полноценный логин бота как пользователя.

- [ ] **Redis для сессий бота**
  В корне проекта есть файл `REDIS_SESSION_SECURITY_PLAN.md`. Необходимо внедрить `telegraf-session-redis` для персистентности состояний.

- [ ] **Типизация API ответов**
  В `webapp` используется JS, но ответы от API не типизированы жестко. Стоит добавить JSDoc или перейти на TypeScript для контрактов данных, чтобы избежать ошибок `undefined` в UI.
